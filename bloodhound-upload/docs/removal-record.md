# Removal record — 2026-07-29

Written as an `ARCHITECTURE.md` changelog entry, then moved here: `ARCHITECTURE.md` ships to
the public ConfigManBearPig repo, and `bloodhound-upload/` does not. A shipped document that
points at a directory the reader cannot see is worse than one that stays silent. The public
changelog therefore records only *that* the upload half was removed; the reasoning lives here,
with the code.

---

**Removed direct BloodHound CE upload from both packages** (ope-60fe), deleting §15 — see the fork's `bloodhound-upload/` for the code, both design plans, the archived §15, and the removed README sections. It existed to shorten the develop→verify loop (one command from credentials to a queryable graph) and stopped paying for itself once the port was feature-complete: every `configmanbearpig` user would have carried an HTTP client, HMAC/Bearer signing, a zip bundler and a schema mutator for a workflow most operators do not use, and `openhound-collector-common` needed `requests` **solely** for it — so the shared library sheds a dependency. Out of the library: the whole `bloodhound/` subpackage (self-contained; nothing else imported it, and MSSQL never touched it) plus its 6 test files. Out of the collector: `bloodhound_schemas.py`, `bloodhound_upload.py`, 3 test files, both `_resolve_upload_mode` / `_dispatch_bloodhound_upload` helpers, and all 16 CLI options (eight on `collect sccm`, eight on `convert sccm`). **Three things deliberately did not change.** The hand-registration of `convert sccm` stays: it still carries `--lookup-file` and `--progress`, the decorator still offers no seam for them, so `app.converter` is still assigned and `openhound` is still a declared dependency for that reason. Both schema JSON files stay in the package — `schema_SCCM.json` is read at runtime by `integration/__init__.py` for the test kit's coverage check, and `schema_MSSQL.json` ships as a deliverable operators now upload by hand — so the "runtime data files live inside the package" rule still has teeth. And `--disable-possible-edges` stays on `collect`, where it changes the graph. It was **removed from `convert`**, where it was a no-op in all but name: possible edges are gated during preprocess (`transforms._read_disable_possible`), so by convert time the decision is already in the lookup DB and the flag's only remaining effect was flipping `is_traversable` in the schema the upload pushed. Verified after removal: both commands still bind, mypy and ruff clean in both packages, and a live `--run-all` collect produced the same 148-node / 454-edge fingerprint.
